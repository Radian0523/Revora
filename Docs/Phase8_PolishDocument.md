# Phase 8: ポリッシュ・ドキュメント — 技術的チャレンジの記録

## 1. AudioManager (miniaudio ラッパー)

### 概要

miniaudio のハイレベル API (`ma_engine`) をラップし、BGM ループ再生と SE ワンショット再生を提供するオーディオ管理クラスを実装した。

### 設計判断

**miniaudio を選択した理由:**
- ヘッダオンリーライブラリであり、ビルドシステムへの統合が最小限で済む
- macOS (CoreAudio) / Windows (WASAPI) / Linux (PulseAudio) のクロスプラットフォーム対応が組み込み済み
- `ma_engine` の高レベル API により、デコード・ミキシング・リサンプリングをライブラリ側に委譲できる
- SDL_mixer と比較して依存が少なく、SDL2 本体以外の追加ライブラリが不要

**SE スロット方式の設計:**
- SE を固定長配列 (`ma_sound[8]`) で管理し、用途ごとにインデックスで再生する
- 動的な SE キュー方式 (名前引きハッシュマップなど) と比較して:
  - メモリ割り当てが発生しない (配列は Application のメンバとして静的確保)
  - 同一 SE の多重トリガー時に seek + start で即時再再生できる
  - スロット数が固定のためデバッグが容易
- レースゲームでは SE の種類が限定的 (5種) であり、動的管理のオーバーヘッドは不要と判断した

**他の選択肢:**
- FMOD / Wwise: 商用ゲームでは標準的だが、ポートフォリオ作品では外部ライセンスの依存を避けたい
- OpenAL: API が古く、macOS での将来的なサポートが不透明
- SDL_mixer: miniaudio と同等の機能だが、SDL_mixer は別途インストールが必要

### 苦労した点

- miniaudio の `ma_sound` は `MA_SOUND_FLAG_DECODE` フラグなしだとストリーミング再生となり、短い SE でもオーバーヘッドが生じる。SE には事前デコードフラグを設定することで解決した
- リトライ時の BGM リセットでは、`ma_sound_stop` → `ma_sound_seek_to_pcm_frame(0)` → `ma_sound_start` の順序を守る必要があった

## 2. LinearAllocator (フレーム単位リニアアロケータ)

### 概要

フレーム内で完結する一時データ (パーティクルのマージバッファなど) の確保に特化したリニアアロケータを実装した。

### 設計判断

**リニアアロケータを選択した理由:**
- 毎フレームの `Render()` でパーティクルをマージする際に `std::vector` を使うと、ヒープ割り当て + 解放が毎フレーム発生する
- リニアアロケータは `Allocate()` がポインタ加算のみ (O(1))、`Reset()` がオフセットゼロクリアのみで、malloc/free のオーバーヘッドを完全に排除できる
- フラグメンテーションが原理的に発生しない

**容量 64KB の根拠:**
- パーティクル最大数: 256 (smoke) + 128 (spark) = 384
- `sizeof(Particle)` ≈ 52 bytes → 384 × 52 = 約 20KB
- 余裕を持たせて 64KB とした

**他の選択肢:**
- スタックアロケータ (LIFO 解放): リニアアロケータで十分なため不採用
- プールアロケータ: 固定サイズの確保には適するが、可変サイズの一時バッファには不向き
- `alloca` (スタック上確保): スタックオーバーフローのリスクがあり、サイズが可変なケースでは安全でない

## 3. ObjectPool\<T\> (テンプレート型オブジェクトプール)

### 概要

パーティクルなど頻繁に生成・破棄されるオブジェクトを、swap-and-pop 方式で O(1) 管理するテンプレートクラスを実装した。

### 設計判断

**swap-and-pop 方式を選択した理由:**
- アクティブ要素は配列の先頭から連続して配置される
  - イテレーション時にキャッシュミスが最小化される
  - GPU へのアップロード時に `memcpy` 一発で転送可能
- `Release(index)` は末尾要素とスワップして `activeCount--` するだけで O(1)
- `Acquire()` は `elements_[activeCount_++]` を返すだけで O(1)
- `std::vector::erase()` の O(N) シフトと比較して、数百個のパーティクルでも安定した性能を維持

**テンプレート + ヘッダオンリーとした理由:**
- パーティクル以外にも将来的に弾丸・エフェクト等に再利用できる汎用性
- ヘッダオンリーにすることでリンク依存を減らし、テンプレートの具体化をコンパイラに任せる

**他の選択肢:**
- フリーリスト方式: 未使用要素をリンクリストで管理する方式。メモリの断片化は防げるが、イテレーション時にキャッシュ局所性が悪化する
- `std::deque`: 連続メモリが保証されず、パーティクルのバッチ処理に不向き
- ECS (Entity Component System): 本プロジェクトの規模ではオーバーエンジニアリング

### ParticleEmitter への移行

既存の `std::vector<Particle> particles_` + `uint32_t activeCount_` による手動プール管理を `ObjectPool<Particle>` に置き換えた。外部 API (`GetActiveParticles()`, `GetActiveCount()`) の戻り値型を `const std::vector<Particle>&` から `const Particle*` + `uint32_t` に変更し、Application 側のマージ処理も `memcpy` ベースに更新した。
